# Hexagonal architecture in this laboratory

Consult [architecture](../../../docs/architecture.md) and the area's decisions. If code contradicts the design, identify the difference before extending it; do not assume that a directory proves independence.

For the concrete change, identify the use case, the rule it protects and external effects. Place pure rules in domain, coordination in application and Payload/HTTP/SQL calls in adapters. Composition injects implementations; the use case does not locate dependencies through a global container.

Ports are defined by the use case's needs and belong to the internal consumer. Use small functions or interfaces and inferred types, without `BaseRepository`, generic entities or mandatory classes. Catalog access is a real boundary; do not create a port per function or copy SDK DTOs or types into the core contract.

Hexagonal architecture decides how the application connects to the outside; DDD helps model its concepts and rules. They complement each other, but neither requires the other's pattern catalog. Preserve useful project structure and modify affected boundaries; do not use a small task to extract every dependency from unrelated files or create empty layers.

In frontend, model search intent, filter changes and use case state outside React. React presents state and initiates actions; the HTTP adapter translates the shared contract. Do not repeat authoritative server hotel rules or turn every visual component into an aggregate.

Payload manages records, users and forms. Its hooks, endpoints and jobs delegate to use cases when product rules are involved. Documents generated by Payload are not the domain model. The adapter maps and validates external boundaries with Zod.

If a boundary changes, state which imports should be allowed/forbidden and why. Check it with the architectural test when available, following the [integrity reference](../hoteles-testing/references/arquitectura.md). Until then, record the pending check; do not simulate a green check. These tests verify dependencies, not agent editing permissions.

Verify behavior through the affected public interface and a representative integration when an adapter changes. Do not write an ADR for a reversible reorganization: use one when there is a tradeoff another developer needs to understand.
