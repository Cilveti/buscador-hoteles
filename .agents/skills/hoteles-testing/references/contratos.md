# Contracts, types and runtime validation

Types check uses of code; Zod checks data arriving at runtime. Neither guarantees by itself that a product rule is correct. Place validation at the boundary that owns the contract, without duplicating schemas across transport, fixture and consumer.

## Single source, independent expectation

- Reuse the production schema and its inferred types (`z.infer`, or `z.input` when transformations make the input differ). Do not maintain a manual interface that repeats its shape or use casts to bypass parsing.
- This does not make the schema its own oracle. Test that it accepts and rejects examples derived from the agreed contract, not only data generated by the same schema.
- For invalid inputs, use unvalidated data or `unknown`; rejecting them is precisely the boundary's job. Do not force an invalid object to appear to have a valid type using `as` or `any`.
- Cover coercions, defaults, limits and extra fields when they change behavior. Distinguish absent data from explicitly empty data, zero or false according to the contract.

## Useful feedback

For representative failures, check the error code and problem path identifying the offending data. For custom rules, keep an actionable message faithful to the domain; verify exact text only when it is part of the public contract. Avoid snapshots of the entire error and internal library messages that may change without altering the contract.

A cross-field rule needs incompatible examples even when every field has the correct type. Public projections need checks that they do not leak administrative fields. Validating only the final shape proves neither permissions nor calculation correctness.
